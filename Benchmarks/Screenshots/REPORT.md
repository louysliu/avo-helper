# 四种截图拼接算法评测

日期：2026-11-05（Asia/Taipei）。输入为 `LocalTestData/Screenshots/1…4`，共 13 张 1206×2622 HEIC，按文件名数字顺序，合计 9 个相邻接缝。使用本机 macOS Release 构建，原图解码后在相同像素输入、相同最终合成器上运行。未针对某组图片调阈值。

**本批样本中 Ekibun 的默认相位相关分支表现最好：第二、三、四组肉眼检查连贯；第一组前两处连贯，最后一处未识别并完整拼接保留。没有一个方案在四组上都达到无缝正确。** 这个结论来自具体图像检查，不是普遍准确率保证。

## 关键视觉证据

* 第 1 组 LongStitch 的首个 `dy=640` 把相似的商品行误配，截断香菜商品的细节；Ekibun/Seamly 对应约 `1054`。LongStitch 的源 session 没有足够可靠地排除这类重复商品布局。
* 第 1 组最后两张未见足以独立确认位置的共同正文锚点。Ekibun 返回 unmatched，因此结果中会重复顶部/底部 UI，这是明确失败回退。Seamly 接受 `1623` 后，输出的“订单服务保障”下缺少输入中的“慢必赔”条目，不能算成功。
* 第 2 组 LongStitch 最初把全部帧判为零位移。使用未修改的 Rust 上游单独复现：每帧 `top=0`，高度一直为 2622，误信固定区域 `(393,393,169)` 的匹配。适配层现将“像素不同但零位移”改为 unmatched，避免静默丢图；没有修改匹配阈值。[对照记录](../../Packages/StitchingKit/Ports/LongStitch/parity/group2-session.txt)
* 第 3 组 ZoomIt 返回 `382`，输出丢失了中间多行订单信息；Ekibun 返回 `1452`，检查可见配送信息、订单号和支付方式连续保留。
* 第 4 组 ZoomIt 返回 `695,906`。第一处遗漏号码保护、公益信息、订单号等，第二处与清楚的商品对应位置存在误差；Ekibun 返回 `1541,928`，输出检查连贯。

## 上游一致性与评测范围

* Ekibun 移植的是上游默认 phase+diff 路径。上游 XML 中 Diff 默认开启、Feature match 默认关闭。FFT 数值适配和验证差异已写入 port 文档，未声称 OpenCV 的逐位数值一致。
* LongStitch 对照保留原始 Rust 源码和可运行 parity harness；固定区域的零位移误认是上游行为。采用相邻帧契约，因此不测上游累积长图回滚/内容刷新功能。
* ZoomIt **Mac** 的未修改原始分辨率 matcher 与本适配器在 9/9 pair 输出上一致。早期外加降采样/NCC 候选改变了结果且产生误拼，最终已移除；最终 JSON 不含该版本。Windows C++ 五帧遮挡 mask 不在本次移植范围内。
* Seamly 的 13 张 HEIC 直接 profile 与公共 RGBA 回转后的 profile 完全一致，排除了方向/通道适配错误。独立调用上游规划/refine 重现了所有接受/拒绝。被拒绝的多处候选仅为 1 个 profile 行位移，被上游 `minEdgeDy=2` 门槛拒绝。
* 统一合成器选择低差异水平硬切、不做补洞或重建；这比较的是各项目移植后的对齐/内容区算法，不是四个原应用的全部产品流程。
* 没有完整长图真值，也没有为所有接缝人工测量精确坐标，因此不报告数值准确率、PSNR 或像素级无损率。对已接受接缝的评价为本次视觉检查。

## 工程验证

* iOS Simulator 的 17 个 app 单元/集成测试通过；最终 ZoomIt 适配调整后又通过四引擎 UIImage→PNG 集成测试。
* Swift package 的契约、已知平移、重复图、失败分段、像素保留、ImageIO 方向/通道、像素预算、LongStitch 改动零位移测试单独运行。
* 四个子 agent 均使用 `gpt-6-astra`、`medium`，提供各自的来源说明与独立 smoke/probe。
* 仅测了本机 macOS 配准耗时和 iOS Simulator 构建/测试，未测 iPhone 真机耗时、峰值内存或随机弹窗覆盖率。单次时序和并发构建负载不适合用作性能排名。

原有算法继续保留作对照；应用默认使用 Ekibun，在选图页右上角“更多选项”菜单可手动切换算法。后续若继续改进，优先以 Ekibun 为基线补充接缝人工修复和真实失败样本，而不是根据当前小样本认定任何候选已经普遍稳定。
